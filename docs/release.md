# 公開手順

新しいバージョンの公開には、事前に利用者の明示的な承認が必要です。main へのマージも別途承認を得てください。

1. `package.json` のバージョンを更新し、`CHANGELOG.md` に `## 0.0.6` のような、バージョンと完全に一致する見出しと変更内容を追加します。バージョン番号は公開する値に置き換えてください。
2. 変更をレビューし、テストを確認したうえで、承認後に main へマージします。
3. 公開の承認を得た後、そのコミットに `package.json` と一致する `v` 付きタグを作成して push します。たとえばバージョンが `0.0.6` の場合は `v0.0.6` です。
4. GitHub Actions の Release を確認します。テストと VSIX の検証、タグと変更履歴の照合、VS Code Marketplace、Open VSX の順に成功すると、同じタグの GitHub Release が作成されます。リリースノートには該当バージョンの変更履歴を使います。検証済み VSIX は Actions の `vsix` artifact として30日間保存されます。

Release ワークフローの手動実行時も、対象としてバージョンタグを選んでください。ブランチからの実行や、タグとバージョンの不一致、変更履歴の欠落・重複・空欄は、ストアへの公開前に失敗します。GitHub Release の作成には、そのジョブの `contents: write` 権限を使用します。両ストアの公開には既存の `VSCE_PAT` と `OVSX_PAT` が必要です。

## 失敗・再実行

- VS Code Marketplace の公開が成功し、Open VSX が失敗した場合、公開済みの Marketplace 版は自動では取り消されません。両ストアの公開状況と Actions のログを確認し、原因を解消して同じ実行を再実行してください。既存の `--skip-duplicate` により公開済みバージョンをスキップします。GitHub Release は両ストアのジョブが成功するまで作成されません。
- GitHub Release の作成だけが失敗した場合も、ストアの公開は取り消されません。権限やエラーを確認し、失敗したジョブを再実行してください。公開済みの同じタグの Release は変更せず成功扱いにします。下書きの場合は失敗するため、内容を確認して対処してください。
- 公開後にタグやバージョンの内容を差し替えて再実行しないでください。公開済みバージョンの修正が必要なら、新しいバージョンを用意し、改めて公開の承認を得ます。
